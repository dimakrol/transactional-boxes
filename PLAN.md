# План: outbox-publisher без фиksированного таймера + поддержка параллельных инстансов

## Контекст

Сейчас `outbox-publisher.service.ts` работает на `@Interval(OUTBOX_POLL_INTERVAL_MS)` (по умолчанию 1000мс): один тик — одна попытка выбрать до `OUTBOX_BATCH_SIZE` записей (`sent_at IS NULL`), последовательно отправить их в Kafka и по одной проставить `sent_at`. Защиты от параллельной работы нескольких инстансов `transactions-service` нет вообще — ни `FOR UPDATE`, ни advisory lock, ни claim-колонки. Плюс отправка в Kafka внутри пачки идёт строго последовательно (await на каждую запись).

Цель: обрабатывать максимум записей за раз, не простаивать между пачками, когда есть работа, и сделать безопасным запуск нескольких инстансов сервиса одновременно.

## Согласованные решения

1. **Планирование.** Оставляем `@Interval(OUTBOX_POLL_INTERVAL_MS)` как точку входа (без замены на собственный рекурсивный `setTimeout`-цикл), но внутри метода — `while`-цикл: тянем пачку → если был реальный прогресс (хотя бы одна запись отправилась) → сразу тянем следующую пачку, без ожидания → если прогресса не было — выходим из цикла и ждём обычный `@Interval`-тик. Существующий флаг `isPolling` остаётся как защита от наложения тиков, если drain затянется дольше интервала.

2. **Защита от параллельных инстансов.** `SELECT ... FROM outbox WHERE sent_at IS NULL AND failed_at IS NULL ORDER BY created_at LIMIT OUTBOX_BATCH_SIZE FOR UPDATE SKIP LOCKED`. Каждый инстанс блокирует свою пачку строк и пропускает уже заблокированные другими — реальный параллелизм между инстансами, а не active-passive. (Проверено отдельно: порядок применения дельт для одного user_id не важен для корректности, т.к. `balance-sync-service` применяет аддитивную дельту через CAS на `version`, а не абсолютное значение — см. `apps/balance-sync-service/src/common/balance.util.ts`.)

3. **Границы транзакции.** Одна транзакция на всю пачку: `BEGIN` → `SELECT ... FOR UPDATE SKIP LOCKED` → параллельная отправка в Kafka (`Promise.allSettled` по всей пачке, не последовательно) → по результатам применяем обновления построчно (`sent_at = now()` для успешных; `attempts = attempts + 1`, и если `attempts >= OUTBOX_MAX_ATTEMPTS` — ещё `failed_at = now()`, для неуспешных) → один `COMMIT` в конце.

4. **Поиск прогресса / бэкофф.** «Есть ли ещё работа» определяем не по заполненности пачки, а по факту: была ли хоть одна успешная отправка в этой итерации. Если весь батч провалился (например, Kafka недоступна) — не молотим сразу снова, ждём обычный интервал. Это защищает от busy-loop при устойчивых сбоях.

5. **Poison-message / лимит попыток.** Новые колонки в `outbox`:
   - `attempts integer NOT NULL DEFAULT 0`
   - `failed_at timestamptz` (nullable)

   Новая переменная окружения `OUTBOX_MAX_ATTEMPTS=3` (по аналогии с `INBOX_MAX_PROCESSING_ATTEMPTS`, для единообразия с inbox-стороной). После исчерпания попыток запись помечается `failed_at` и перестаёт попадать в выборку (`AND failed_at IS NULL`), плюс структурированный `logger.error` с id записи. Дальше лога (алертинг, Sentry и т.п.) не идёт — такой инфраструктуры в проекте сейчас нет.

6. **Индекс.** Частичный индекс под сам паттерн выборки:
   ```sql
   CREATE INDEX ON outbox (created_at) WHERE sent_at IS NULL AND failed_at IS NULL;
   ```
   Без него по мере роста таблицы каждая пачка — full table scan, что сводит на нет выигрыш от параллельных инстансов.

## Файлы к изменению

- `apps/transactions-service/src/outbox/outbox-publisher.service.ts` — основная логика (пп. 1–5 выше).
- `apps/transactions-service/src/db/schema.ts` — колонки `attempts`, `failed_at` в таблице `outbox`.
- Новая drizzle-миграция (`db:generate:transactions-service`) — добавление колонок + партиционный индекс.
- `.env`, `.env.example`, `docker-compose.yml` (сервис `transactions-service`) — новая переменная `OUTBOX_MAX_ATTEMPTS=3`.

## Верификация

Стек уже поднят локально (`docker compose up -d`, 6 контейнеров). После реализации:
- Прогнать `scripts/load-test.js` против уже поднятого стека.
- Убедиться в отсутствии дублей/пропусков при параллельной обработке (дедупликация по `idempotency_id` как контроль).
- Проверить по логам, что при провале отправки запись действительно ретраится, а после `OUTBOX_MAX_ATTEMPTS` — помечается `failed_at` и перестаёт мешать другим записям.
